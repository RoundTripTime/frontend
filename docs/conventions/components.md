# 컴포넌트 분리 원칙

## 목적

화면 구현 단위를 Screen / Container / Presentational / 공용 컴포넌트로 분리한다.

## 분류 기준

| 분류 | 역할 | 포함 범위 |
| --- | --- | --- |
| Screen | 라우트에 직접 연결되는 화면 단위 | 화면 목적, 진입 경로, 화면 전체 레이아웃 |
| Container | 화면의 데이터와 동작을 연결하는 단위 | 조회, 변경, 이동, 제출, 필터링, 상태 연결 |
| Presentational | 화면에 보이는 UI 조각 | 카드, 리스트, 섹션, 버튼 묶음, 입력 영역 |
| 공용 | 여러 화면에서 반복 사용되는 UI 또는 유틸 성격 컴포넌트 | 장소 카드, 플랜 카드, 탭, 시트, 토스트, 인디케이터 |

## Screen

- `Screen Specs`의 화면 ID 하나를 기본 단위로 둔다.
- 하단 탭, 상세 화면, 작성/편집 화면처럼 진입 경로가 있는 단위는 Screen으로 둔다.
- Screen은 화면 전체 배치와 Container 조합을 담당한다.
- Screen 내부에 서버 조회, 변경 요청, 복잡한 입력 처리 로직을 직접 두지 않는다.

## Container

- Screen에서 필요한 데이터 조회와 사용자 동작을 Presentational 컴포넌트에 전달한다.
- 장소 필터링, 장소 수락/거절, 플랜 생성, 플랜 저장, 공유 URL 생성, 광고 시청 결과 처리처럼 동작을 연결한다.
- 라우팅 이동이 필요한 이벤트는 Container에서 처리한다.
- 동일 Screen 안에서만 쓰이는 Container는 해당 Screen 하위에 둔다.

## Presentational

- props로 받은 데이터와 이벤트만 사용한다.
- 장소 카드, 플랜 카드, 포스트 카드, 장소 리스트, 일자별 섹션, 입력 Step처럼 화면에 표시되는 조각을 담당한다.
- 서버 조회, 전역 상태 변경, 라우팅 호출을 직접 하지 않는다.
- 비활성화, 선택됨, 로딩, 빈 상태처럼 표시 상태는 props로 받는다.

## 공용 컴포넌트

- 두 개 이상의 화면에서 반복되는 UI만 공용으로 둔다.
- 장소 카드, 플랜 카드, 하단 탭, 공유 시트, 토스트, 로딩 인디케이터처럼 화면 목적과 무관하게 재사용되는 단위를 공용으로 둔다.
- 특정 화면의 동작이나 데이터 모델을 공용 컴포넌트 안에 넣지 않는다.

## 판단 순서

1. 진입 경로가 있는 화면이면 Screen으로 둔다.
2. 데이터 조회, 변경, 이동, 제출을 연결하면 Container로 둔다.
3. props만 받아 UI를 그리면 Presentational로 둔다.
4. 두 화면 이상에서 반복되면 공용으로 승격한다.
